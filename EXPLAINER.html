Por que o EXPLAINER da v3.6.0 agora passa pelo Plannotator?

execução 20260823-175129-2804543·válido para a versão v3.6.0·documentado em 2026-08-23

Resposta em uma frase

Porque, na v3.6.0, o EXPLAINER.html deixou de ser gerado por um script fixo e passou a ser uma explicação didática delegada a um sub-agente, e o Plannotator é o runtime de render/anotação cujos tokens de tema a skill de render aplica ao arquivo final — instalado automaticamente quando falta.

Como o leitor é misto ou desconhecido, este documento constrói o conteúdo para o novato, com o andaime (passo a passo) recolhível em <details> para quem já conhece o orquestrador pular.

O novo fluxo do EXPLAINER

Quatro etapas encadeadas trocam o script fixo por uma explicação construída sob regras didáticas.

O caminho crítico está no passo de renderização: é onde o Plannotator entra — se a skill de render não estiver disponível e destravada, o arquivo não sai. A figura abaixo marca essa etapa em destaque; o texto volta a apontá-lo no segmento O runtime do Plannotator.

Antes × depois, a diferença

Comparar é desenhar o que cada rota adiciona — uma rota nova no lugar da antiga.

Três artefatos foram removidos: o script generate-explainer.sh, o template html-explainer.html e a pasta templates/. No lugar, entram a delegação didática e o runtime Plannotator.

O contrato de instalação do Plannotator

Quatro peças têm de existir para a entrega acontecer — e o script de auto-instalação garante as quatro.

O check-plannotator.sh --install instala o binário em modo --minimal quando falta (mínima 0.19.1). Nesta execução o Plannotator já estava instalado em v0.27.6 e o setup já estava pronto — nada precisou ser instalado; só foi documentado.

O destrave é o passo crítico: a skill de render chega com disable-model-invocation: true; sem a linha removida (e o flag allow_implicit_invocation ajustado), a ordem "invoque a skill de render" vira uma ordem impossível de cumprir e o agente cairia no fallback de escrever HTML na mão — exatamente o que a v3.6.0 eliminou.

Segmentos

O que esta execução tocou e por quê — em passos com título próprio.

1 · Estado verificado: o Plannotator já estava pronto

A tarefa pedia "instalar o plannotator se não tiver". A checagem da máquina mostrou que nada precisava ser instalado:

  • Binário em /home/ondokai/.local/bin/plannotator, v0.27.6 (mínima exigida 0.19.1); o probe plannotator annotate imprime o usage e sai rc 0, sem abrir navegador.
  • Setup html-explainer PRONTO: binário OK, skills visual-explainer e plannotator-visual-explainer OK, invocação pelo modelo liberada, 7/7 agent skill dirs com as duas skills.

O requisito foi conferido e a auto-instalação documentada para o caso de ausência futura.

2 · O runtime do Plannotator (o caminho crítico)

Plannotator é o runtime de render/anotação: um binário local que sobe um servidor e abre a UI de anotação. No fluxo novo, a skill de render plannotator-visual-explainer aplica os tokens de tema do Plannotator ao arquivo final. Este é o gargalo apontado na Figura 1: sem render, não existe EXPLAINER.

3 · Auto-instalação, quando faltar

Se o binário faltar em outro ambiente, scripts/check-plannotator.sh --install o instala em modo --minimal — só ~/.local/bin, mínimo 0.19.1, sem sudo, sem npm -g, e nunca sobrescreve uma instalação existente.

4 · Docs e about atualizados

O README.md ganhou bullet "Plannotator como runtime do EXPLAINER (auto-instalado)" nas Novidades v3.6.0 e o item "Plannotator — AUTO-INSTALADO" em Requisitos. O "about" da skill (a description no frontmatter do SKILL.md) passou a descrever o EXPLAINER final didático v3.6.0 gerado por sub-agente seguindo a html-explainer-agent-skill, sem limite de tempo, salvo em EXPLAINER.html no lugar.

5 · O orquestrador rodou e fechou

Uma onda de docs (onda1-about-plannotator) foi integrada por squash-merge no commit a02037f com o gate de snapshot verde (GATE_BUILD bash -n; GATE_TEST check-install --quiet; sem linter dedicado). A testing subwave foi NO-OP e a validação rodou o gate completo no integrado. O EXPLAINER.html deste ciclo é o dogfooding #2 pelo fluxo novo (a execução usa a própria entrega que documenta). A versão ficou em v3.6.0 (mudança documental) e o commit + push para o GitHub é o passo final da execução.

Dobrado — o que quem já conhece o orquestrador pode pular

Andaime para o novato, recolhível para o experiente.

Para quem já trabalha com o deep-orchestrator, o Segmento 5 já resume tudo: uma onda de docs, gate verde, commit a02037f. O passo a passo granular abaixo atende a quem está vendo o orquestrador pela primeira vez.

Passo a passo do ciclo de orquestração (para o novato)
  1. FASE 1 — ANALYZE: lê a tarefa e mapeia a estrutura do repositório.
  2. FASE 2 — PLAN: decompõe a tarefa em sub-tarefas, cada uma na sua worktree, e em ondas paralelas.
  3. FASE 3 — EXECUTE-ONDA: dispara os sub-agentes, revisa adversarialmente e integra cada um por squash-merge, com o gate rodando em snapshot.
  4. FASE 4 — COMMIT-FINAL: roda o gate completo, registra só o que a execução produziu, gera o EXPLAINER.html pelo fluxo novo e entrega o relatório.

Nesta execução só houve uma onda: a de documentação (onda1-about-plannotator), porque a instalação já estava pronta e o restante era redigir docs/about.
